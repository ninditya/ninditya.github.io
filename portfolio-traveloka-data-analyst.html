Context: Routing every customer query to an LLM is the default architecture and the most expensive one. In a customer care setting, a large share of incoming queries are repetitive and do not require generative reasoning. Problem: How much LLM spend can be removed without degrading answer quality, and where exactly should the escalation threshold sit?
Architecture — 4-Tier Confidence-Based Routing
Pipeline: queries are classified by an SBERT embedding + LinearSVC classifier, then resolved by regex filter, template response, RAG retrieval, or full LLM call depending on confidence score — each tier priced and latency-profiled independently.
Live Demo & Production Monitoring
Live chat demo: each response is tagged with its routing tier, confidence score, latency, and per-query cost — the cost/quality trade-off made visible to the end user.
Grafana Cloud dashboard: request rate, P99 latency, routing distribution, and estimated cost savings vs. an all-LLM baseline — the same monitoring pattern used for release gating in Case 1.
Result
0.9305 Macro F1 maintained while LLM inference cost fell 88%, at approximately 50ms routing latency. The threshold is tunable, making the accuracy vs. cost trade-off an explicit business decision rather than an implicit one.
Why this matters for Customer Care
This is the exact question a Customer Care analytics function needs answered: where does AI actually reduce cost-to-serve without degrading CSAT, and where should human/LLM/rule-based handling boundaries sit.
Served in production shape
FastAPI service with Prometheus/Grafana monitoring on confidence distribution and routing drift — deployable observability, not a notebook result.
Stack: Python · SBERT · LinearSVC · FastAPI · Grafana · Docker

Context: Hiring decisions were made against job descriptions rather than against the measurable profile of people who already perform well in the role. Problem: Benchmark 2,010 candidate records against top-performer characteristics using SQL alone, with logic transparent enough to be audited by non-technical stakeholders.
SQL Matching Algorithm Architecture — 17 CTEs
PostgreSQL · 17-CTE Query Chain
Phase 1
Top-performer benchmark extraction
Filter top-rated employees, compute PERCENTILE_CONT for continuous scores and MODE() for categorical traits. Output: a benchmark profile object.
CTEs 1–4
Phase 2
Gap scoring per candidate
For each of 2,010 candidates: compute distance from benchmark on each pillar, normalize to a 0–1 scale, apply inverse scoring (closer to benchmark = higher score).
CTEs 5–10
Phase 3
Weighted composite & ranking
Configurable pillar weights, PERCENT_RANK() window functions for department-level ranking. Final output: candidate_id, composite_score, rank, tier classification.
CTEs 11–17
Key SQL Techniques Used
-- Benchmark extraction: median score per pillar WITH top_performers AS ( SELECT * FROM employees WHERE rating = 5 ), benchmark AS ( SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY pillar_score) AS pillar_p50, MODE() WITHIN GROUP (ORDER BY education_field) AS edu_mode FROM top_performers ) -- Final ranking with department-level percentile SELECT candidate_id, composite_score, PERCENT_RANK() OVER (PARTITION BY department ORDER BY composite_score DESC) AS dept_rank FROM scored_candidates ORDER BY composite_score DESC;
Result
A ranked candidate matching system where every score component traces back to an explicit SQL rule — demonstrating analytical SQL depth beyond aggregation and joins.
Dashboard behavior
Manager selects a role vacancy → system computes match scores for all 2,010 candidates → ranked output with tier classification, plus an AI-generated job profile summary per vacancy.
Data quality
Employees with missing ratings are excluded, not imputed. All 17 CTEs are documented with inline comments; a star schema separates candidate facts from assessment dimensions.
Stack: PostgreSQL · advanced SQL (CTE, window functions, PERCENTILE_CONT) · Streamlit · OpenRouter

Context: Approving a high-risk loan risks the principal; rejecting a sound applicant loses interest income and a good customer — credit risk scoring has to get both directions right. Problem: Build a GOOD/BAD classifier using only information available at origination (not post-disbursement outcomes), on a target that is only ~11.2% BAD, and translate the output into underwriting decisions rather than a single accuracy number.
Methodology — Leak-Free by Construction, Threshold as a Business Decision
Feature Audit → Threshold Tuning → Out-of-Time Validation
Audit
75 raw columns disposition-audited, imbalance compared head-to-head
Post-disbursement fields (total_pymnt, recoveries, out_prncp) dropped; outlier caps fit on the training fold only. class_weight/scale_pos_weight tested directly against SMOTE across 6 model variants.
75 → 27 features
Threshold
F1-optimal vs. cost-based decision threshold
F1-optimal threshold (0.585) tuned on out-of-fold probabilities; a separate expected-loss threshold (PD × LGD × EAD) tested at 0.070 — same review-capacity trade-off logic as the routing threshold in Case 2.
2 thresholds compared
Validate
Chronological split + PSI drift check
Train on 2007–Aug 2014 originations, test on Aug–Dec 2014 — ROC-AUC held at 0.705 (vs. 0.694 on a random split), confirming the model generalizes forward in time rather than memorizing an economic period.
PSI = 0.11
Where Risk Concentrates & What Drives the Score — Grade/Tenor Bad Rate & SHAP
Bad-loan rate rises monotonically from grade A (~4%) to grade G (~28%). 60-month loans and non-mortgage borrowers show consistently higher bad rates — the basis for the tenor-based pricing recommendation below.
SHAP beeswarm (XGBoost): per-prediction, additive attribution — high int_rate sharply raises predicted risk, high income is protective. Same driver ranking a Logistic Regression coefficient view confirms independently.
Business recommendation
Grade G / 60-month loans carry a 26.6% bad rate — 2.4× the portfolio baseline — just 2.8% of volume but 6.5% of all bad loans in test. Recommendation: a tenor-based risk premium (+2–3pp) and mandatory manual underwriting review for this segment, prioritized because the low volume keeps review cost small relative to the loss it prevents.
Self-correction, proven not assumed
Retraining the same model with post-disbursement columns reattached pushes accuracy to 95.4% — confirming the reported 70–74% accuracy is genuine signal, not leakage. Calibration curves separately show raw probabilities run high (mean ≈0.46 vs. an actual 11.2% base rate) — ranking and threshold decisions stay valid, but raw probabilities need calibration before being read as literal PDs.
Threshold is a business lever, not a constant
The cost-minimizing threshold (0.070) flags ~89% of applications for review at that illustrative loss ratio — mathematically correct but operationally unworkable without an explicit review-capacity constraint. Documented as a next step rather than silently defaulted to 0.5.
Stack: Python · pandas · scikit-learn · XGBoost · imbalanced-learn (SMOTE) · SHAP · Flask
