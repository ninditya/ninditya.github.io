02 · Test Plan & Scope

Scoped like production. Even though the bank is fictional.

Performance and penetration testing sit with dedicated teams in a real org, so they're explicitly out of scope here — but everything a manual QA owns end-to-end is in.

In Scope
  • Functional: Intrabank, BI-FAST, Virtual Account, QRIS (scan & pay)
  • Negative: insufficient balance, limits, invalid input, session timeout
  • API testing: POST /transfer, POST /qris/pay, GET /transaction/status
  • Database validation: balance mutation, transaction log, settlement status
  • Regression: Login, Check Balance, Transaction History
  • SIT against BI-FAST & QRIS switching sandboxes
Out of Scope
  • Performance / load testing — owned by a dedicated Performance team
  • Security penetration testing — owned by a dedicated Security team
  • Test automation — manual this phase; regression suite is the automation candidate next sprint

Entry & exit criteria

03 · Test Scenario & Case Design

The interesting bugs live in the edge cases.

38 high-level scenarios across Transfer, QRIS, and light non-functional checks — split into positive, negative, and edge case — broken down into 30 detailed test cases with steps, test data, and expected results.

5 edge cases worth designing on purpose

ScenarioWhy it matters
Double-tap "Send" within 1 secondClassic bug pattern that causes real financial loss if the second tap isn't debounced or idempotency-checked.
Connection drops right after submitMoney can leave the account while the screen still says "Failed" — a reconciliation gap, not just a UI glitch.
BI-FAST switching times outFunds leave the sender but never arrive — needs an automatic reversal or an honest "Pending" state.
QR Merchant ID mismatch at settlementMoney can settle to the wrong merchant if the QR payload isn't cross-checked against backend master data.
Two devices scan the same static QR at onceConcurrency bug — a race condition on balance updates is easy to miss with sequential manual testing alone.

05 · Defect Management

6 bugs. 3 of them touch real money.

Logged in JIRA-style format — Summary, Environment, Steps to Reproduce, Expected vs. Actual, Severity, Priority. Every one below is reproducible live in the prototype: set the build toggle to v1.4.0-QA to trigger it, then flip to v1.5.0-FIX and repeat the same steps to verify the fix.

BUG-SGP-001Critical

Double debit on rapid double-tap of "Send"

Root CauseNo debounce on the submit button and no idempotency key on POST /transfer — the second tap created a second, fully separate transaction.
FixDisable the button on first tap; add an idempotency key server-side.
✓ Closed — verified via SQL duplicate-check query
BUG-SGP-002Critical

UI shows "Failed" while the backend recorded success

Root CauseClient assumed failure on timeout instead of querying actual transaction status — balance was already debited and backend status was SUCCESS.
FixClient auto-queries transaction status after any timeout, before showing a failure state.
✓ Closed — status now reconciled automatically
BUG-SGP-003Major

No auto-reversal when BI-FAST switching times out

Root CauseNo scheduled job to reverse funds or resolve a "Pending" state once the SLA is exceeded — money stayed debited indefinitely.
FixScheduled auto-reversal job after a 15-minute SLA, with user notification.
✓ Closed — verified via Pending-past-SLA query
BUG-SGP-004Critical

Expired QR still gets processed for payment

Root CauseNo expiry_time check on client or backend before hitting POST /qris/pay — payment succeeded past the QR's validity window.
FixValidate expiry on both client (fast UX) and backend (source of truth).
✓ Closed — verified via Postman assertion on errorCode QR_EXPIRED
BUG-SGP-005Major

No Merchant ID cross-check at settlement

Root CauseSettlement trusted the Merchant ID embedded in the QR payload with no cross-check against registered merchant master data.
FixValidate QR Merchant ID against master data before final settlement.
✓ Closed — verified via merchant cross-check query
BUG-SGP-006Minor

Negative amount accepted with no client-side validation

Root CauseForm allowed -100000 through to the confirmation screen, surfacing a vague backend error instead of failing fast.
FixAdd client-side validation for the amount field.
✓ Closed
Found during regression, not the original test pass: BUG-SGP-007 — transaction history sorted incorrectly after a date-format change elsewhere in the app. It was outside the Transfer/QRIS scope entirely, which is exactly the point of running a full regression suite instead of only retesting what changed.
06 · API & Database Validation

If it only looks right in the UI, it isn't verified.

This is the layer that separates "clicked through the screens" from a QA who can prove root cause to a developer with a request/response pair or a query result — not just a claim.

Postman collection structure

SigmaPay QA Collection/ ├── Auth/ │ └── POST /auth/login ├── Transfer/ │ ├── POST /transfer/inquiry │ ├── POST /transfer │ └── GET /transaction/status └── QRIS/ ├── POST /qris/decode └── POST /qris/pay 
// pm.test assertions after POST /transfer
pm.test("Status code is 200", () => {
  pm.response.to.have.status(200);
});
pm.test("Response has transactionId", () => {
  const body = pm.response.json();
  pm.expect(body.transactionId).to.match(/^TRX/);
});
pm.test("Amount matches request", () => {
  const req = JSON.parse(pm.request.body.raw);
  pm.expect(pm.response.json().amount).to.eql(req.amount);
});

SQL validation — proving root cause from the data

-- A.3 · No duplicate transactions from double-tap (BUG-SGP-001)
SELECT type, amount, destination_account, COUNT(*) AS total,
       array_agg(trx_id) AS trx_ids
FROM transactions
WHERE account_no = '8801 2345 6789'
  AND created_at >= NOW() - INTERVAL '5 minutes'
GROUP BY type, amount, destination_account
HAVING COUNT(*) > 1;
-- v1.4.0-QA (buggy): 1 duplicate row. v1.5.0-FIX: 0 rows.

-- B.5 · Pending transactions past the 15-minute SLA (BUG-SGP-003)
SELECT trx_id, amount, status, created_at,
       NOW() - created_at AS pending_duration
FROM transactions
WHERE status = 'PENDING'
  AND created_at < NOW() - INTERVAL '15 minutes';
-- v1.5.0-FIX: 0 rows — auto-reversal job resolves them in time.

09 · Lessons Learned

QA in banking isn't about clicking buttons. It's about protecting money that moves.

Edge cases are where money bugs hide

Happy-path testing found zero of the three Critical defects. Double debit, ambiguous status, and reversal timing only surface under edge-case and concurrency conditions — exactly the cases easiest to skip under deadline pressure.

Verify below the screen, not just on it

BUG-SGP-002 and BUG-SGP-004's real root cause was in the backend, not the UI. A SQL query and a Postman assertion proved it — a screenshot alone would not have.

Regression discipline scales

A 26-item checklist, reused every cycle, caught BUG-SGP-007 in a module that wasn't even part of the original release. That's the return on writing the checklist once.

Saying "simulation, not production" is a credibility move

This project proves STLC discipline end-to-end. Overstating it as production banking experience would be the first thing a good interviewer catches — being precise about the difference is the more senior answer.
