02 · Test Plan & Scope

I scoped it the way I would a real project. The bank being fake didn't change that.

Performance and penetration testing sit with dedicated teams in a real org, so they're explicitly out of scope here — but everything a manual QA owns end-to-end is in.

In Scope
  • Functional: Intrabank, BI-FAST, Virtual Account, QRIS (scan & pay)
  • Negative: insufficient balance, limits, invalid input, session timeout
  • API testing: POST /transfer, POST /qris/pay, GET /transaction/status
  • Database validation: balance mutation, transaction log, settlement status
  • Regression: Login, Check Balance, Transaction History
  • SIT against BI-FAST & QRIS switching sandboxes
Out of Scope
  • Performance / load testing — owned by a dedicated Performance team
  • Security penetration testing — owned by a dedicated Security team
  • Test automation — manual this phase; regression suite is the automation candidate next sprint

05 · Defect Management

I found 6 bugs. 3 of them would have cost someone real money.

Logged in JIRA-style format — Summary, Environment, Steps to Reproduce, Expected vs. Actual, Severity, Priority. Every one below is reproducible live in the prototype: set the build toggle to v1.4.0-QA to trigger it, then flip to v1.5.0-FIX and repeat the same steps to verify the fix.

BUG-SGP-001Critical

Double debit on rapid double-tap of "Send"

I found this by doing something a real user would do without thinking twice — tapping "Send" twice, fast, because the app felt like it was lagging. It wasn't just the UI: the transfer actually went through twice. I checked the database and found two identical transactions logged seconds apart. Root cause: the submit button had no debounce, and POST /transfer had no idempotency key, so the second tap was treated as a brand-new, valid request. I recommended disabling the button the moment it's tapped and adding a server-side idempotency key.
✓ Closed — I reran the same duplicate-check query after the fix and got zero rows
BUG-SGP-002Critical

UI shows "Failed" while the backend recorded success

This one showed up when I killed the connection right after hitting submit — a scenario I tested on purpose, since it's exactly what happens on a bad signal in real life. The app showed "Failed." I didn't trust that at face value, so I checked the balance and the transaction log directly: the money was already gone and the backend status was SUCCESS. The client had just assumed failure because the request timed out, instead of asking the backend what actually happened. Fix: after any timeout, the client has to query the real transaction status before it's allowed to show a failure screen.
✓ Closed — I forced the same timeout again post-fix, status now reconciles automatically
BUG-SGP-003Major

No auto-reversal when BI-FAST switching times out

I simulated a BI-FAST switching timeout to see what would happen to money in transit — and nothing happened. There was no scheduled job to reverse the funds or resolve the "Pending" state once the SLA passed, so the balance just stayed debited indefinitely with no path back. In a real bank, that's exactly the kind of thing that turns into a customer dispute. I recommended a scheduled auto-reversal job that fires after a 15-minute SLA, with a notification to the user either way.
✓ Closed — I queried for anything still Pending past 15 minutes; after the fix, zero rows
BUG-SGP-004Critical

Expired QR still gets processed for payment

I let a QR code expire on purpose, then tried paying with it anyway. It went through. Neither the client nor the backend was checking expiry_time before hitting POST /qris/pay, so a payment could succeed well past the QR's validity window. I recommended validating expiry on both sides: client-side for fast feedback, backend as the actual source of truth.
✓ Closed — the same expired QR now returns errorCode QR_EXPIRED in Postman instead of a success response
BUG-SGP-005Major

No Merchant ID cross-check at settlement

I found this by editing the Merchant ID inside a QR payload before scanning it — something a malicious-but-legitimate-looking QR could do just as easily. Settlement went through anyway, trusting whatever Merchant ID was embedded in the QR with no check against the registered merchant master data. That's a real risk: money could settle to the wrong merchant and nobody would notice until reconciliation. I recommended cross-checking the QR's Merchant ID against master data before final settlement.
✓ Closed — a query joining the two now catches a mismatched ID before settlement, not after
BUG-SGP-006Minor

Negative amount accepted with no client-side validation

A small one, but still worth catching: I typed -100000 into the amount field and it sailed straight through to the confirmation screen before failing with a vague backend error. Nothing on the client side stopped an obviously invalid amount from getting that far. I added client-side validation so it fails immediately and clearly instead of letting the user reach confirmation first.
✓ Closed
I found this one during a regression pass, not the original test run — which is exactly why I run the full checklist instead of only retesting what changed. BUG-SGP-007: transaction history was sorting incorrectly after a date-format change somewhere else in the app, in a module that had nothing to do with Transfer or QRIS.
06 · API & Database Validation

The UI told me everything was fine. The database told a different story.

This is the layer that separates "clicked through the screens" from a QA who can prove root cause to a developer with a request/response pair or a query result — not just a claim. These are basic negative and robustness checks at the API layer, not formal penetration testing — that remains a dedicated Security team's scope.

  pm.expect(body.transactionId).to.match(/^TRX/);

  pm.expect(pm.response.json().amount).to.eql(req.amount);

SQL validation — proving root cause from the data

-- A.3 · No duplicate transactions from double-tap (BUG-SGP-001)
SELECT type, amount, destination_account, COUNT(*) AS total,
       array_agg(trx_id) AS trx_ids
FROM transactions
WHERE account_no = '8801 2345 6789'
  AND created_at >= NOW() - INTERVAL '5 minutes'
GROUP BY type, amount, destination_account
HAVING COUNT(*) > 1;
-- v1.4.0-QA (buggy): 1 duplicate row. v1.5.0-FIX: 0 rows.

-- B.5 · Pending transactions past the 15-minute SLA (BUG-SGP-003)
SELECT trx_id, amount, status, created_at,
       NOW() - created_at AS pending_duration
FROM transactions
WHERE status = 'PENDING'
  AND created_at < NOW() - INTERVAL '15 minutes';
-- v1.5.0-FIX: 0 rows — auto-reversal job resolves them in time.

09 · Lessons Learned

What I actually walked away with. Not the textbook version.

Testing the happy path first told me nothing

None of the three Critical bugs showed up when I just tested things working normally. I only found the double debit, the ambiguous status, and the reversal timing once I started testing double-taps, dropped connections, and timeouts on purpose — the exact cases that are easiest to skip when you're behind schedule.

A screenshot wouldn't have proven anything

BUG-SGP-002 and BUG-SGP-004 both looked fine on screen — the actual problem was sitting in the backend. I only caught it because I went and checked the database and the API response directly. If I'd stopped at the UI, I would've closed both as "can't reproduce."

Writing the checklist once paid off later

BUG-SGP-007 was in a module that had nothing to do with what I was originally testing. I only caught it because the 30-item regression checklist runs every cycle, not just when something changes. Writing it once meant I didn't have to think about what to re-check — I just ran it.

I'd rather be precise than impressive

This project proves I can run STLC discipline end to end — that part is real. What isn't real is production banking experience, and I'd rather say that clearly than have an interviewer catch me overstating it. Being precise about the difference is the more senior answer anyway.
