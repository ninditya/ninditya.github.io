-- Validate no duplicate transaction from double-tap (BUG-SGP-001) SELECT type, amount, destination_account, COUNT(*) AS transaction_count, array_agg(trx_id) AS trx_ids FROM transactions WHERE account_no = '8801 2345 6789' AND created_at >= NOW() - INTERVAL '5 minutes' GROUP BY type, amount, destination_account HAVING COUNT(*) > 1; -- Buggy build (v1.4.0-QA): 1 duplicate row. Critical Defect — BUG-SGP-001
Double debit on rapid double-tap of "Send" — no debounce, no idempotency key on POST /transfer. Fix: disable button on first tap + server-side idempotency key. Closed, verified via the SQL query above.

Problem: Most QA postings name one automation tool, but interviews probe judgment across tools — why Playwright over Selenium, how to triage a flaky test versus a real bug. Solution: The identical 29-case regression suite (Login, Cart, Sort, Checkout, Known-Issue Regression) written three times over in Playwright, Cypress, and Selenium, run against the real live saucedemo.com — not a mock — with results compared framework-to-framework and re-verified over time instead of trusted from a single run.

Framework Divergence — BUG-003
Playwright consistently caught the seeded "Sorting is broken!" alert; Cypress never did, same day, same run. Likely cause: the two dispatch a <select> change event differently — not a bug in either tool, a real signal the defect is interaction-style-sensitive.
Tooling Bug, Not an App Bug — LOGIN-08
Cypress failed cy.visit('/cart.html') on an HTTP 404 before any JS ran; Playwright ignored the status and let client-side routing redirect normally. Root cause traced with response.status(), not guessed — fixed with { failOnStatusCode: false }.
Defect Regression, Verified Over Time
Re-running all 7 seeded bugs found 2 (BUG-004, BUG-006) no longer reproduce and 2 more (BUG-003, BUG-007) are framework-dependent — only BUG-001 and BUG-005 are unambiguously still active.

Problem: The production LLM QA discipline run at Flip — hallucination rate, answer grounding, fallback triggers — can't be demonstrated with Flip's confidential data. Solution: The identical methodology applied to two RAG systems built and owned outright — a banking intent router and an Indonesian health-misinformation checker — including a chatbot caught fabricating a support phone number that appears nowhere in its source data.
Evaluation Pipeline — Real Output, Not Hardcoded Examples
Generate → Catch → Detect → Calibrate
Generate
Eval Data From the Real Pipeline
Banking: 12 FAQ queries paraphrased away from exact wording, run through the real rag.py + llm_client.py. Health: RAGEngine run once across all 20 claims, predictions cached — both frameworks grade real system output, not a mock.
32 cases
Catch
Hallucination in the Wild
The ungrounded LLM escalation tier (no retrieval context) fabricated a support phone number that appears nowhere in banking_faq.json — caught by inspecting real pipeline output, before any paid judge run.
1 fabrication
Detect
LLM-as-Judge, Kept Separate
Custom DeepEval GEval metric ("No Fabricated Contact Details") plus Faithfulness / Relevancy / Contextual Precision-Recall via DeepEval + Ragas. Judge model (Claude / GPT-4o-mini) is never the model being graded.
GEval + Ragas
Calibrate
Fallback Triggers
HealthTruth-AI's TIDAK LENGKAP (insufficient-context) verdict fails safe on a flu-vaccine claim the corpus doesn't cover, but flattens a nuanced ibuprofen/COVID claim to HOAX instead of hedging — a real calibration gap, not just a pass count.
18/20 correct
Judge Kept Separate From the App
Banking Intent Router judged with Claude; HealthTruth-AI judged with GPT-4o-mini via OpenRouter. Neither judge is the model generating the answer it grades — a model scoring its own output is the exact blind spot this exists to catch.
Honest About What's Verified
Real pipeline execution and the fabricated-phone-number finding are directly inspectable now. The full paid-judge numeric score run (Faithfulness/Hallucination across every case) is built and ready, not yet executed — stated plainly, not rounded up.
Retrieval Baseline
Banking retrieval top-1 accuracy measured at 10/12 (0.83) on a real run. Both misses were semantically adjacent intents (e.g. "card_arrival" retrieved as "activate_card") — a reasonable embedding-retrieval edge case, not a broken pipeline.
