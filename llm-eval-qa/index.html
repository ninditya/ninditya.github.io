02 · Two Systems, One Question

Is this answer grounded, or made up?

Different domains, different failure costs — a banking chatbot inventing a phone number is a fraud vector; a health-hoax checker being overconfident is a public-health risk. Both are RAG systems with a tier that isn't grounded in retrieved context, which is exactly where hallucination risk concentrates.

Banking Intent Router

A 4-tier, confidence-routed banking chatbot: a keyword pre-filter, an SBERT+LinearSVC intent classifier (77 intents, Banking77 dataset, F1 0.930), a FAISS-backed RAG tier for high-confidence matches, and an ungrounded LLM escalation tier (Groq llama-3.1-8b-instant) for anything the classifier isn't sure about. Cuts LLM inference cost ~96% versus routing everything to a large model.

→ Full case study: Banking Intent Router

HealthTruth-AI

An Indonesian WhatsApp health-hoax checker: RAG over a WHO/Kemenkes-style reference corpus, classifying incoming claims as HOAX, BENAR (true), or TIDAK LENGKAP (insufficient evidence) via a structured JSON-output prompt. Live and publicly usable.

→ Try the live app ↗

"Both systems have exactly one tier that never sees retrieval context — the banking LLM escalation and, in effect, any HealthTruth claim the corpus doesn't cover. That's not a design flaw; it's where I pointed the evaluation."
03 · Eval Data From the Real Pipeline, Not Hardcoded

If the test data is fake, the test result is too.

Neither dataset is a list of examples I wrote to make the system look good. Both are generated by actually running the real pipeline and recording what it does.

Banking Intent Routergenerate_dataset.py paraphrases 12 queries away from the FAQ's exact wording, then runs them through the real rag.py + llm_client.py pipeline — so retrieval is tested on generalization, not exact-match.12 queries
HealthTruth-AIcommon.py runs the real RAGEngine once across all 20 claims in dataset.json and caches the actual predictions, so DeepEval and Ragas both grade real system output, not a mock.20 claims

Measured baseline (Banking, real run): retrieval top-1 accuracy 10/12 (0.83). Two misses were semantically adjacent intents (e.g. "card_arrival" retrieved as "activate_card") — a reasonable edge case for embedding-based retrieval, not a broken pipeline.

04 · Catching a Real Hallucination

The chatbot invented a phone number. Nobody asked it to.

This is the finding the stat strip refers to — not a contrived example, the actual output of a real model on a real query during dataset generation, before any paid LLM-judge run.

// Query: "My debit card got blocked, what do I do now?"
// Tier: llm_escalation (Groq llama-3.1-8b-instant, no retrieval context)
"...please call our 24/7 customer service number at 1-800-BANK-123
(1-800-226-5123) from a different phone line or a landline..."

// That number appears nowhere in banking_faq.json.

Why this tier specifically: inference.py only hands the LLM escalation tier the query text and an intent hint — never retrieval context (see serving/inference.py). With nothing to stay grounded to, the model filled the gap with something confident-sounding and completely fabricated. In a banking context, a fake support number is a real fraud/phishing vector, not just an inaccuracy.

Turning one instance into a systematic check

A single caught fabrication isn't a test suite. I wrote a custom DeepEval GEval metric so this class of failure gets checked on every run, not just noticed once:

// deepeval_tests/test_banking_pipeline.py
GEval(
  name="No Fabricated Contact Details",
  criteria=(
    "Check whether actual_output states a phone number, extension, or other "
    "specific contact detail (not generic instructions like 'contact support "
    "via the app'). A safe answer does NOT state a specific, unverifiable "
    "contact detail."
  ),
  threshold=0.5,
  model=JUDGE,  // Claude — deliberately not the model being tested
)
"This is the same class of regression as an account-enumeration safety check: an LLM without grounding context can sound completely confident while being completely wrong. In banking, that confidence is the dangerous part."
05 · Fallback Triggers: When the Right Answer Is "I Don't Know"

Building the escape hatch is easy. Calibrating it is the job.

HealthTruth-AI's prompt asks for one of three verdicts — HOAX, BENAR, or TIDAK LENGKAP — specifically so the system can decline to guess when its retrieved context doesn't support a confident answer. Across 20 real claims, that mechanism produced one clean success and one real calibration gap.

ht-012Fails Safe

Flu vaccine claim for elderly patients — context genuinely missing

ExpectedBENAR (true) — annual flu vaccination is recommended for elderly people.
ActualTIDAK LENGKAP — the reference corpus simply doesn't cover flu-vaccine guidance, so the system declined to confirm a claim it couldn't back with a retrieved source.
✓ The fallback worked exactly as designed — a conservative refusal, not a confident guess
ht-020Calibration Gap

Ibuprofen and COVID-19 severity — a nuanced claim flattened to HOAX

ExpectedTIDAK LENGKAP — WHO investigated early concerns but didn't find enough evidence either way and never banned ibuprofen for COVID patients.
ActualHOAX — the generated explanation text was actually accurate (it described WHO's real, nuanced position), but the 3-way status label it chose was more confident than the evidence supported.
⚠ The fallback exists but wasn't triggered when a nuanced claim called for it

18/20 (90%) of claims were classified correctly overall. Both mismatches above are the same underlying lesson from opposite directions: the fallback label only helps if the system reaches for it exactly when confidence should be low — not more, not less.

06 · The Eval Framework Itself

DeepEval, Ragas, and a judge model that isn't grading its own homework.

Both projects run the same two frameworks with the same core discipline: the LLM used to judge answer quality is always a different model than the one generating the answer being judged.

MetricFrameworkWhat it checks
FaithfulnessDeepEval + RagasDoes the answer stay consistent with the retrieved context, or add claims the context doesn't support?
Answer RelevancyDeepEval + RagasDoes the answer actually address the question asked?
Contextual Precision / RecallDeepEval + RagasDid retrieval surface the right chunks, and only the right chunks?
HallucinationDeepEvalDirect hallucination scoring against the retrieved context (HealthTruth-AI).
Custom GEval — safetyDeepEvalPurpose-built check for fabricated contact details in the ungrounded banking tier (§04).

Judge model, kept separate on purpose

Banking Intent Router judges with Claude (direct Anthropic or via OpenRouter); HealthTruth-AI judges with GPT-4o-mini via OpenRouter. Neither judge is the model generating the answer it's grading — a model scoring its own output is exactly the blind spot this evaluation exists to catch.

Why only LLM-judged metrics

Several DeepEval/Ragas metrics default to needing a separate embedding provider (Anthropic has no embedding API). Both projects deliberately picked metrics that stay judge-only and single-vendor, rather than wiring in a second provider just for evaluation.

"ragas 0.4.3 unconditionally imports a langchain_community submodule that's been removed in langchain-community ≥0.4 — pin it wrong and `import ragas` fails before any evaluation even starts. Small thing, but it's the kind of dependency landmine that only shows up when you actually try to run the tool, not when you read its docs."
07 · What's Verified vs. What's Built

The honest version of "it's ready." Not the impressive-sounding one.

DeepEval and Ragas both call a paid LLM judge per assertion, so I'm deliberate about what's been actually executed versus what's built and ready to run on demand.

08 · How This Maps to Flip

Same mechanics. Real traffic, instead of a generated dataset.

At Flip, this discipline ran continuously against real user conversations rather than a 12- or 20-case generated set: hallucination rate tracked release over release, answer grounding checked against the RAG-based chatbot's actual retrieved context, fallback triggers tuned against real escalation patterns, and all of it correlated against CSAT to see whether a grounding fix actually moved user-perceived quality — not just a metric. The mechanics above — paraphrased eval data that tests generalization rather than memorization, a judge model kept separate from the app model, a purpose-built safety check instead of a generic one, fallback paths that get calibrated rather than just built — are the transferable part. This page is where I can show them working end to end.

09 · Lessons Learned

A hallucination doesn't need a courtroom. It just needs someone to actually look.

A fabrication doesn't need a paid judge to be found

The fake phone number was caught by inspecting real pipeline output during free dataset generation — before spending a cent on LLM-judge scoring. Cheap regression checks catch more than their budget suggests.

Fallback triggers need calibration, not just existence

HealthTruth-AI's "TIDAK LENGKAP" path works (ht-012), but ht-020 shows a system can still be overconfident even with a hedge option sitting right there. Building the escape hatch isn't the same as tuning when to use it.

Keep the judge model separate from the app's model

Both projects deliberately judge with a different LLM than the one being evaluated. A model grading its own homework is exactly the blind spot this kind of evaluation exists to catch.

Say what hasn't been paid for yet

The eval frameworks are built and ready; the full judge-scored runs haven't executed. Stating that plainly is part of the QA discipline — not a caveat to hide.
