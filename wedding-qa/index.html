QA Automation Case Study Digital wedding invitation · live system, real guests

My wedding invitation has real guests. So I tested it like a product.

Each guest gets a personal link over WhatsApp. The page takes their RSVP and wishes, answers questions through a rule-based chatbot, and shows the gift bank accounts to immediate family and close friends only. A bug here shows a bank account to the wrong person or loses someone's RSVP, and the guests are my own family and friends. So I wrote 81 formal test cases and backed them with 477 unit and API tests and 54 Playwright browser tests on three emulated phones, all running on every push.

01 · Why It Needed Testing

The risky part isn't the design. It's who gets to see the bank account.

I started from what could actually go wrong for a guest or for us, then wrote down the rules the system must never break. Every test case traces back to one of those rules or to a section of the spec.

Five rules the system must never break

Rule 1Bank account data never reaches the browser unless the server has just verified the guest's role.
Rule 2Every limit is checked on the server. The checks in the page are for convenience only.
Rule 3Fail closed: an unknown group, an empty role or a typo is treated as a general guest; an unknown or deactivated link gets a 404.
Rule 4A guest's role is their personal override, else their group's default, else general guest, worked out in one place.
Rule 5Link codes are 10 random characters, never derived from a name or a phone number. Unknown and deactivated links get the same 404.

02 · Test Plan & Scope

Three levels of testing. Each covers what the one below it can't.

Rules and limits are tested at the API, because that is where they are enforced. The browser tests check that a guest on a phone actually gets through the page. Real phones opened from WhatsApp stay manual, because an emulator is not WhatsApp.

03 · Test Case Design

81 test cases, each traced to a rule and to the test that runs it.

Every case has an ID, the requirement it comes from, steps, an expected result and the name of the automated test that covers it. The first 55 are automated as unit and API tests. 04 · Test Automation

The browser tests run the real production build. Only the database is fake.

Playwright builds and starts the site the way it is deployed, with one difference: the database address points at a small stand-in server written for the tests. Each test asks that server for a brand-new guest, plays the scenario on a phone profile, then reads the guest's record back to check what was really saved.

Playwright
18 scenarios on 3 phone profiles, in parallel. Every test seeds its own guest, so tests never share an RSVP, wishes or device slots.

Sample 1 · A general guest gets no bank data, checked six ways

One scenario, six separate proofs: the gift chip is absent from the chat, typed questions get a thank-you text, the page never even asks the server for the accounts, a direct request from the guest's own verified browser gets a 403 with an empty body, no account holder or account digits appear anywhere on the page, and the gift-view log in the database stays at zero.

Sample 3 · Fixtures that explain themselves

Two fixtures apply to every test. The first skips the suite, with a written reason, once the RSVP deadline has passed and the page no longer looks the way the tests describe. The second handles a real difference between browsers: WebKit refuses a Secure cookie over local http, Chromium accepts it.

// These tests describe the invitation as it is before the wedding: RSVP open, no "Today!" card. The server's
// clock decides that (docs/spec.md §8.3), and a test cannot turn it back. From the RSVP deadline on they are
// skipped, with this reason, instead of failing: write tests for the day-of and after-event pages then.
const RSVP_DEADLINE = Date.parse(eventContent("pernikahan").rsvpDeadline);

// The site under test runs as a production build over plain http on this machine. Its verification
// cookie is marked Secure (lib/verify.ts), which Chromium still accepts from 127.0.0.1 but WebKit does not.
// For WebKit only, the cookie the server set is stored again without that one mark; its name, value and
// expiry are the server's own. In production the site is https, so the mark stays.
export const test = base.extend<{ beforeTheWedding: void; secureCookieOverHttp: void }>({
  beforeTheWedding: [
    async ({}, use, testInfo) => {
      testInfo.skip(Date.now() > RSVP_DEADLINE, "The RSVP deadline has passed: the invitation no longer looks the way these tests describe.");
      await use();
    },
    { auto: true },
  ],
  secureCookieOverHttp: [
    async ({ context, browserName }, use) => {
      if (browserName === "webkit") {
        await context.route("**/api/verify", async (route) => {
          // route.fetch() puts the server's cookie in this browser's jar, still marked Secure.
          const response = await route.fetch();
          const marked = (await context.cookies()).filter((c) => c.secure);
          if (marked.length) await context.addCookies(marked.map((c) => ({ ...c, secure: false })));
          const { "set-cookie": _stored, ...headers } = response.headers();
          await route.fulfill({ response, headers });
        });
      }
      await use();
    },
    { auto: true },
  ],
});

08 · Lessons Learned

What this suite taught me. Mostly about what a test can't see.

A message on screen is not proof

After every action that should save something, the test reads the guest's record back from the database: the RSVP, the number of wishes, the device count, the gift-view log. A toast that says "sent" doesn't show that anything was stored.

Don't weaken the product to pass a test

The verification cookie is marked Secure. Chromium accepts it from a local http address and WebKit does not, so on the iPhone profiles a guest would never stay verified. A fixture stores the server's own cookie again without that one mark, for WebKit only. The production cookie is unchanged.

A test that depends on the date should say so

The page changes after the RSVP deadline, by the server's clock. From then on these tests would fail for a reason that isn't a bug, so they skip themselves and print why. The pages for the event day and after it still need their own tests.

A test run must not be able to reach real guests

The test servers use unusual ports, never reuse a server that is already running, and get a fake database key that overrides my real settings file. That is also why CI needs no secrets at all.
