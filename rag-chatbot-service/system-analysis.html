01 · Introduction

Purpose, scope and basis of this specification

1.1 Purpose

This document specifies the requirements, the analysis model and the design of HealthTruth-AI as built in its v1 production refactor. It is an as-built specification: the requirements below describe behaviour that exists, and the gaps are recorded as gaps rather than restated as plans.

1.2 Scope

The system answers health questions and adjudicates health claims against a curated corpus of documents from BPOM, IDI, WHO and Kemenkes. It embeds the query, searches a vector store, and generates only from what it retrieved. Answers are shaped by a health profile the user supplies per session, which the server never stores.

In scope
  • Question answering at three answer depths
  • Claim adjudication returning a schema-constrained verdict
  • Dense retrieval over a persistent vector store with a quality gate
  • Grounding enforcement — no retrieved context, no generation
  • Stateless personalisation by profile context injection
  • Prompt-injection defence at the prompt boundary
  • Graceful degradation on provider quota exhaustion
  • Authenticated document ingestion
Out of scope
  • Medical diagnosis, prescription or dosing advice
  • User accounts, authentication and stored health records
  • Conversation memory across requests
  • Clinical review or regulatory certification of answers
  • Retrieval quality benchmarking — not yet built (§19, §23)
  • Operational dashboards and alerting — not yet built
  • Document versioning and source-quality filtering

02 · Overall description

A retrieval gate in front of a language model

The system's defining property is negative: there is a path in which it declines to generate. If retrieval returns nothing above the score gate, the model is never called and the user is told the corpus has no coverage.

05 · Problem case & evolution

Two problems the system solves together

The first problem is misinformation: health claims circulate through messaging apps and are believed. The second is subtler and is the reason a search engine is not a sufficient answer — even a claim with some scientific basis carries generic advice. A supplement that is harmless for a healthy adult can interact badly with a blood thinner; high-dose ginger has real contraindications; turmeric and gallbladder disease is a documented interaction. The question the system is designed to answer is therefore not "is this claim true" but "is this claim true for this person, given their conditions and medications".

5.1 Design responses

Grounded generation

Answers must trace back to a document in the corpus. When retrieval returns nothing, the model is not called and the system reports insufficient context instead of producing an opinion.

Stateless personalisation

Age, conditions, allergies and medications shape the answer, but no profile is stored on the server. The context travels with the query and is discarded with the response.

Reliability first

Generation quota exhaustion returns the retrieved passages themselves. An unreachable store falls back to keyword search. Every failure point has a defined degraded state.

5.2 What changed between v0 and v1

Layerv0 — course submissionv1 — production refactor
Vector storeIn-memory index, lost on every restart; documents re-added by hand after each redeployManaged vector store, persistent across redeploys and cold starts
PipelineA single raw chain — a failure was visible but not locatableNamed nodes with conditional routing; a failure localises to the node that produced it
PersonalisationOne flat prompt template for every readerProfile context injected per request, so the answer is shaped by the reader's own data
ArchitectureOne file, global state, tight couplingSeparate classes with constructor injection and a single composition root
Error handlingCrash on quota exhaustionLayered fallback — retrieved context served in place of a generated answer

The persistence change is the one that decided the rest. An index that dies on restart cannot hold a curated corpus, so every other property — the score gate, the no-context path, authenticated ingestion — depends on the store surviving a deploy.

6.1 UC-02 specification — fact-check a claim

PreconditionsThe graph is compiled and the store is reachable, or the keyword fallback is available.
Main flow1. The reader pastes a claim, at most 2,000 characters. 2. The client prepends the profile context if one is set. 3. The endpoint validates the payload and starts the timer. 4. The text is sanitised. 5. The text is embedded. 6. The store returns up to three passages above the score gate, de-duplicated. 7. Routing finds context present and proceeds to the answer node. 8. The prompt is assembled with the claim inside its own delimiter block and the passages inside a trusted block, and a JSON response type is requested. 9. The verdict, summary, explanation and sources are parsed. 10. The response returns with elapsed time and a degradation flag set false.
Alt. flow A — no contextAt step 7 the context is empty: routing goes to the no-context node, no generation call is made, and the verdict returned is insufficient evidence.
Alt. flow B — quota exhaustedAt step 8 the provider signals a quota or availability failure: the retrieved passages are returned as the answer, the degradation flag is set, and the client shows a banner explaining that the text is quoted directly from the corpus.
Alt. flow C — malformed outputAt step 9 the response is not valid JSON: a structured fallback is returned instead of raising.
Exception — store unreachableAt step 6 the store cannot be reached: the in-memory keyword search answers instead, with reduced recall.
PostconditionsNothing is written. No profile, claim or answer is persisted.

07 · Process flow

The graph, and the exit that skips the model

Splitting the pipeline into named nodes buys one thing that a single function cannot: a failure has a location. A retrieval error is visible in the retrieve node's state and a generation error in the answer node's, so diagnosis does not begin with reading a stack trace. The same structure also leaves room for a reranking or query-rewriting node without rewiring the pipeline.

14 · Retrieval design

Vector search with a quality gate

14.1 Configuration

ParameterValueRationale
Embedding modelGemini embedding-0013,072 dimensions, semantic-similarity task type, multilingual
Embedding task typesemantic_similarityExplicitly trained for retrieval, not classification or clustering
Index typeQdrant — cosine similarityHosted, persistent, supports filtering by metadata
Top-k3Three passages fit in a prompt without ballooning token count
Score threshold0.4Unvalidated. Chosen to exclude off-topic results; no labelled evaluation set exists (§14.2)
DeduplicationExact match on payload textA question might match the same passage twice with tiny score differences; de-duplicate to keep the strongest match
Fallback strategyIn-memory BM25 keyword searchRuns on a mirror built at start-up. Searches if Qdrant is unreachable but only from docs already in memory.

14.2 Gap: unmeasured quality

The 0.4 threshold is a guess. No labelled query-to-passage set exists, so recall at 1 and 3 are unknown. An evaluation set of fifty queries each with known-relevant passages would show whether a threshold is burying relevant results or accepting garbage. This is R-01 in the risk register and the first roadmap item.

15 · Prompt & security design

Delimiters, sanitisation and no stored secrets

15.1 Prompt structure

Every prompt has one invariant structure: instructions, then a TRUSTED_CONTEXT block holding the retrieved passages, then a USER_QUERY block holding the user's text, then a mode-specific closing. User content never lives outside its delimiter block.

Example: Ask mode
You are a health information assistant. Use only the provided context.

<TRUSTED_CONTEXT>
{{ passage 1 }}
{{ passage 2 }}
{{ passage 3 }}
</TRUSTED_CONTEXT>

<USER_QUERY>
{{ question + profile context }}
</USER_QUERY>

Provide a {{ mode }}-level answer in {{ language }}.

15.2 Sanitisation

Before assembly, the user text is cleaned: null bytes stripped, runs of three or more newlines collapsed to two. These are defensive measures against both accidental and deliberate injection, though the XML delimiters are the load-bearing boundary.

15.3 Credentials and storage

  • Embedding and generation credentials are separate environment variables, so an exhaustion in one does not break the other.
  • No credentials are logged; errors are sanitised before they reach logs.
  • API keys for document ingestion are validated against an in-memory set read at start-up, not against a database.
  • The profile is never stored — it is assembled by the client, sent with the query, and discarded with the response.
16 · Reliability design

Degraded states, not crashes

16.1 Generation quota exhaustion

When the generation provider signals quota or availability failure, the error classifier recognises it as transient. The retrieved passages become the answer; they are joined by a newline-separated rule. The degraded flag is set true, and the client renders a banner explaining that the text is quoted directly from the corpus, not generated.

16.2 Store unreachability

If Qdrant is unreachable, the workflow falls back to the in-memory keyword index. This index is built at start-up from the documents already in memory and is exact, not approximate. Its recall is lower than vector search — it misses paraphrases — but it is available. The response still carries a context_used list so the client knows what was retrieved and by which method.

16.3 Both retrieval and generation fail

If retrieval is empty and generation is exhausted, the workflow has no answer to return. The no-context node responds with insufficient evidence. This is a 200 response with an empty context_used list.

16.4 Configuration credibility

The system will not start if required environment variables are missing. It will start with warnings if optional ones (store, generation credentials) are absent, but those paths degrade at runtime. A missing embedding credential is fatal — there is no fallback for embedding.

19 · Observability specification

Gap: no observability yet

Neither the backend nor the Streamlit app emit metrics. Every request is measured locally (elapsed time is returned in the response), but there is no centralised logging, no metrics dashboard, and no alerts. This is NFR-14 in the requirements and the highest-priority item in the roadmap.

23 · Limitations & roadmap

Known gaps and the work ahead

Limitations
  • Retrieval threshold is unvalidated; no labelled evaluation set exists.
  • No metrics or dashboards — observability is entirely absent.
  • No conversation memory; each query is independent.
  • No document versioning; source management is manual.
  • Generation is not yet multi-modal; images and tables cannot be handled.
  • Ingestion is authenticated but not logged or rate-limited.
Roadmap, priority order
  1. Build retrieval evaluation set. Fifty queries with labelled relevant passages; measure recall at 1 and 3 to validate the threshold.
  2. Metrics and dashboards. Emit Prometheus metrics; set up a Grafana dashboard to watch traffic, latency, error rates and degradation.
  3. Rate limiting on ingestion. Prevent bulk uploads from exhausting quota; log all ingestion events.
  4. Conversation memory. Stateless for now, but a follow-up should maintain context within one session.
  5. Document versioning and filtering. Track source age; allow curators to mark sources as deprecated; surface version info in the answer.
  6. Multi-modal retrieval. Handle images and tables in the corpus; embed and retrieve them.
24 · Glossary

Terms as used in this document

GroundingThe design principle that no answer is generated without retrieved context. If retrieval is empty, the system declines to answer.
DegradationA graceful fallback when a provider is exhausted. Retrieved passages are joined and returned as the answer; the flag signals the client to display them as quotes, not as generated text.
Stateless personalisationA health profile that shapes the answer but is never stored. The profile travels with the request in a structured block prepended to the query.
Profile contextThe serialised health profile — age, conditions, allergies, medications — formatted as a structured block and prepended to the question before embedding and generation.
Embedding modelGemini embedding-001, 3,072 dimensions, trained on semantic-similarity tasks. Separate credential from the generation model.
Score thresholdA cosine-similarity cutoff (currently 0.4) below which retrieved passages are discarded. Unvalidated.
Keyword fallbackAn in-memory BM25 index built at start-up from documents already loaded. Used when Qdrant is unreachable.
Transient errorA quota or availability failure from the generation provider, classified as recoverable and causing degradation rather than failure.
XML delimiterA structural boundary around user content in the prompt (<USER_QUERY>) that protects against prompt injection.
