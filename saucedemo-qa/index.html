01 · Why This Project

Automation postings ask for proof. Not a tool list.

Automation QA postings ask for the same concrete things, over and over: Playwright or Cypress, Selenium as a fallback, CI/CD, and the judgment to tell a genuine bug from a flaky test. Rather than claim all three as buzzwords, I wrote the identical 29-case regression suite in Playwright, Cypress, and Selenium and ran it against SauceDemo's real, public demo site — so every claim on this page is something I can walk through, not recite.

02 · Scope & Test Accounts

Scoped around what's actually there. Not a generic checklist.

SauceDemo doesn't have a real backend, a payment gateway, or a registration flow — so scope was drawn around what's actually there, not a generic e-commerce checklist copied from somewhere else.

In Scope
  • Login: 6 test accounts — valid, invalid, case-sensitive, empty fields, locked-out, logout
  • Cart: add, remove from 2 different pages, Continue Shopping
  • Sort: all 4 options (Name A–Z/Z–A, Price low–high/high–low)
  • Checkout: single & multi-item, required-field validation, special characters, total calculation
  • Regression against 7 seeded bugs across 4 special test accounts
Out of Scope
  • Register — the site has no registration feature at all
  • Payment processing — no real payment gateway; checkout uses fixed dummy data
  • Address validation — only required-field checks exist, no real format validation
  • API testing — SauceDemo is 100% client-rendered with no public API to test

05 · When Frameworks Disagree

Same claim, same site. Opposite verdict.

For the 26 cases run in both Playwright and Cypress, the overall pass rate matched exactly. But 2 of the 6 known-issue checks disagreed on the same day's run — which turned out to be the single most useful finding of this whole cycle.

BUG-003 · Sort
Playwright: FAIL
Cypress: PASS — same day
BUG-007 · Dashboard speed
Playwright: PASS
Cypress: FAIL — same day

BUG-003 (sort throws a JS error for error_user): Playwright always caught the "Sorting is broken!" alert; Cypress never did, on the same run. Most likely cause — Playwright and Cypress dispatch a change event on a <select> differently: Cypress simulates it in JavaScript, Playwright emulates input closer to real browser behavior via Chrome DevTools Protocol. The broken-sort logic in error_user is probably sensitive to exactly that difference — meaning the bug doesn't show up in every interaction style, which is more useful to know than a flat yes/no.

BUG-007 (slow dashboard for performance_glitch_user): the check's threshold is 5 seconds — tight enough that Cypress's interactive Test Runner (more rendering overhead than Playwright's headless run) tipped it over the line while Playwright stayed under. Likely a threshold that's too tight for a stable pass/fail across tools, not a delay that actually changed.

A cross-framework bug that wasn't SauceDemo's fault

Adding LOGIN-08 (cart access without login redirects to the login page — one of the 3 cases from the triage table above) turned up a genuine tooling difference, not an app bug. Here's the actual chain, not a guess.

// Cypress, running LOGIN-08
cy.visit() failed trying to load: https://www.saucedemo.com/cart.html

The response we received from your web server was: > 404: Not Found

Checked via Playwright's response.status(): saucedemo.com's server genuinely returns HTTP 404 for a direct hit on /cart.html. It isn't a real redirect — /cart.html is a client-side route (React Router), not something the server recognizes. But that 404 response body still ships the same React bundle, so the app boots anyway, and with no active session, client-side routing sends it to / within about 2 seconds.

FrameworkDefault behavior on a non-2xx status
Playwright (page.goto())Doesn't care about the status code — continues, lets the page's JS run. toHaveURL() auto-retries until the client-side redirect lands.
Cypress (cy.visit())Fails hard on any non-2xx status, before the page's JS gets a chance to run — needs an explicit { failOnStatusCode: false } to get past it.
 
// The fix, in auth.cy.ts
cy.visit('/cart.html', { failOnStatusCode: false });

LOGIN-08's test case description was also corrected in the CSV — it originally just said "redirects to login," which undersold how much more is actually going on. This was a bug in test assumptions, not a change in SauceDemo's behavior, so it stayed out of the Bug Report.

"Two frameworks reporting different results isn't automatically a bug in one of them — sometimes it's a real signal that a behavior is sensitive to exactly how you interact with the page, which is more useful information than a single tool's yes/no."

None of that would have surfaced without actually re-running the checks and comparing tools — not from trusting the last write-up.

09 · Lessons Learned

Automation doesn't replace judgment. It just gives judgment better evidence.

Never trust old bug docs without re-verifying

3 of 7 previously-recorded bugs turned out to have already changed status. Regression testing exists to catch drift, not just to confirm what's already written down — a lesson this cycle proved directly, not in theory.

Two tools, two answers — and that's data, not noise

BUG-003 and BUG-007 disagreed between Playwright and Cypress on the same day. Understanding why they disagreed mattered more than picking a "correct" tool — the disagreement itself was the finding.

Debug the environment, not just the code

When Cypress's Electron binary was blocked by a sandboxed dev environment, the fix wasn't reinstalling repeatedly. Checking codesign/spctl first confirmed it was an environment issue, not broken code.

Triage before you add

5 externally-written test cases were checked against the live site before merging — 3 added, 2 rejected as duplicates. Validating a claim is not the same as accepting it, and that difference is most of what a test-case review actually is.
