01 · Introduction

Purpose, scope and basis of this specification

1.1 Purpose

This document specifies the software requirements, the analysis model and the design of the Banking Intent Router. It is written as an as-built specification: every requirement, interface and design decision recorded here is traced to a file in the implementation rather than to an intended future state.

1.2 Scope

The system classifies an inbound banking support query into one of 77 intents, derives a calibrated confidence score from that classification, and uses the score as a routing signal across four answer tiers. It exposes the decision through a JSON API, a browser chat client and a Prometheus metrics endpoint, and it is retrained by a continuous-integration pipeline.

In scope
  • Intent classification over 77 Banking77 classes
  • Conversational pre-filter and four-tier routing
  • Retrieval from a curated 59-entry FAQ knowledge base
  • LLM escalation across four interchangeable providers
  • Per-request cost and latency accounting
  • Prometheus instrumentation and Grafana delivery
  • Automated preprocessing, training and image publication
Out of scope
  • Customer authentication and session identity
  • Core banking integration; no transaction is executed
  • Account-specific data lookup — answers are generic
  • Conversation memory across turns; every call is stateless
  • Languages other than English for classification
  • Human agent hand-off and ticketing
  • Model governance sign-off and regulatory approval

1.3 Intended readership

Engineering reviewers assessing the design, ML engineers extending the model or thresholds, and operators running the serving stack. Sections 03–05 are readable without ML background; sections 14–15 assume familiarity with sentence embeddings and probability calibration.

05 · Business case

Why a router pays for itself

A chatbot that sends every query to a large model pays the most expensive unit price for its most repetitive traffic. The router's premise is that confidence is a usable proxy for "has this been asked before".

Savings are computed in estimate_cost_savings() during training, over the confidence distribution of the held-out split: actual cost is the sum of each prediction's tier price, the baseline is the row count multiplied by the LLM price, and the reported percentage is one minus their ratio. The same map is applied per request at serving time as a Prometheus counter, so the training estimate and the production figure are directly comparable.

Boundary of the claim

The cost map is an internal assumption, not a vendor invoice. It encodes the relative order of magnitude between a static answer, a vector lookup and a hosted completion. Absolute currency figures should be restated from real pricing before being used in a budget.

6.2 UC-01 specification

PreconditionsA model artifact and encoder name are loaded; the FAQ index is built or retrieval is reported unavailable.
Main flow1. The customer submits a query. 2. The system records input length and increments in-flight requests. 3. The pre-filter finds no conversational match. 4. The query is embedded. 5. The classifier returns a class index and a calibrated probability vector. 6. Confidence is taken as the maximum probability. 7. A tier is selected. 8. The tier produces an answer. 9. Confidence, tier, intent, cost and latency are observed. 10. The response is returned and the client renders the routing card.
Alt. flow A — greetingAt step 3 the utterance matches the greeting or farewell set: the system answers from the static map with tier 0, intent id −1, confidence 1.0 and cost 0, and skips steps 4–7.
Alt. flow B — retrieval unavailableAt step 8 on tier 1 or 2 the retrieval module is absent: the answer field stays null, the tier decision is still reported, and the client falls back to its local template map.
Alt. flow C — provider failureAt step 8 on tier 3 the provider call raises: the error is logged, a static support message is returned in the LLM answer field, and the response remains 200.
Exception — model absentAt the precondition, no model is loaded: the endpoint answers 503 with an explanatory detail and the client shows a service-unavailable notice.
PostconditionsOne request counter, one latency observation, one confidence observation, one tier counter, one intent counter and one cost increment are recorded. No query text is stored.
07 · Process flow

The four-tier routing activity

Two properties of this flow are deliberate. First, the pre-filter runs before the encoder, so "hi" never pays for an embedding pass and never pollutes the intent distribution. Second, the confidence bands are contiguous and exhaustive: every query lands in exactly one tier, and there is no path in which the router declines to answer.

11 · Class design

Three collaborators and their contracts

11.1 Design notes

Shared encoder

The retrieval module receives the router's encoder rather than constructing its own. One MiniLM instance serves both classification and retrieval, halving memory and guaranteeing that query and FAQ vectors share a space.

Optional dependency

Retrieval is a nullable attribute. If FAISS is missing or the FAQ file is absent, loading logs a warning and continues; the tier decision still happens and the answer field is simply empty.

Provider demotion

The client selects a provider from one environment variable and silently demotes to the deterministic mock when the matching key is missing. A misconfigured deployment answers with a plausible support message instead of failing at start-up.

14 · Routing & threshold design

Turning a probability into a spending decision

14.1 Why calibration is load-bearing

A linear support vector classifier emits decision-function margins, not probabilities. Margins are not comparable across classes and have no fixed scale, so a threshold expressed against them would drift with every retraining. The classifier is therefore wrapped in a sigmoid calibration over three cross-validation folds, which maps margins onto a probability simplex. The routing threshold then means the same thing from one release to the next — this is the reason the wrapper is a requirement rather than a refinement.

14.2 Threshold placement

ConstantValueRationale
HIGH_THR0.55Above this point the predicted intent is reliable enough to answer from a single canned entry without showing sources. Set with reference to the confidence histogram, where the dense upper mode sits well clear of 0.55.
MID_THR0.30Between the two thresholds the model is directionally right but not certain, so the answer is retrieved with three sources shown — the user can judge the match. Below it, retrieval would be guessing.
hint gate0.25Inside the escalation tier the predicted label is passed to the model as a context hint only above 0.25; below that the prediction is noise and would mislead the completion.
low-confidence0.60Drift indicator only. The share of the last hundred predictions below 0.60 is published as a gauge; it has no effect on routing.

14.3 Single source of truth, and where it is duplicated

Training-side scripts import thresholds, the cost map and the decision function from one shared module, so tuning the bands changes every experiment at once. The serving process declares the same four constants locally, because the serving image ships without the training package. This is a deliberate duplication with a maintenance cost: any threshold change must be applied on both sides, and §22 records it as a live risk (R-05).

Invariant

The bands are contiguous, exhaustive and ordered so that a higher confidence never selects a more expensive tier. Any future band must preserve that monotonicity, otherwise the cost model stops holding.

16 · Interface design

The client discloses its own routing

The chat client is a demonstration surface as much as a support surface. Every answer carries the tier that produced it, the confidence that selected the tier, the intent label, the measured latency and the unit cost — so the routing behaviour specified in §07 is observable without reading logs.

18 · CI/CD design

Retraining as a pipeline, not a ritual

#StageBehaviourFailure mode
1TriggerPush to the default branch touching the training project, or manual dispatch—
2EnvironmentCheckout, Python 3.10, pinned MLflow, scikit-learn, pandas, numpy, matplotlib and seabornHard fail on resolution conflict

Two design choices are worth naming. The run id is written to a file by the training script rather than parsed from log output, which makes the hand-off between stages 3 and 6 explicit and testable. And the artifact upload is the only tolerated failure in the chain, because remote tracking already holds the same files — every other stage is load-bearing and fails loudly.

Gap

The pipeline publishes on every successful run. There is no quality gate comparing the new macro F1 against the deployed value, so a regression can be pushed as long as training completes. §23 lists this as the first roadmap item.

19.1 Delivery paths

Two paths carry the same registry. In development, Prometheus scrapes the metrics endpoint every fifteen seconds and Grafana reads from Prometheus. In hosted deployment, where no scraper can reach the container, a background task collects every router_* sample, encodes it as a remote-write request and pushes it to Grafana Cloud on the same interval — protobuf assembled by hand and snappy-compressed, so no additional client library enters the image. Push failures are logged and the loop continues; telemetry never takes the service down.

23 · Limitations & roadmap

What the current release does not do

Limitations
  • Thresholds were placed by reading the confidence histogram, not by optimising a cost-weighted objective. There is no evidence that 0.55 and 0.30 are the best pair.
  • Retrieval quality is unmeasured. No labelled query-to-entry set exists, so recall at k for the fifty-nine-entry base is unknown.
  • Tier 1 answers without disclosing a source, so a wrong retrieval at high confidence is invisible to the user.
  • The service is stateless per turn; a follow-up question is classified with no memory of the previous one.
  • Classification is English-only. Only the pre-filter recognises Indonesian, and only for greetings.
  • Publication has no quality gate, and the serving process does not assert that its thresholds match the trained ones.
Roadmap, in priority order
  1. Metric gate in CI. Compare the candidate's macro F1 and calibration against the deployed run and refuse to publish a regression.
  2. Threshold optimisation. Sweep both thresholds against a cost-weighted objective over the held-out confidences and record the frontier, replacing a read of the histogram with a chosen operating point.
  3. Retrieval evaluation set. Label a hundred queries with their correct knowledge-base entry; measure recall at 1 and 3 before any retrieval change.
  4. Share the thresholds. One package imported by both sides, or a start-up assertion that fails loudly on divergence.
  5. Move blocking work off the event loop. Encode and retrieve in a thread executor so concurrency is bounded by workers rather than by the loop.
  6. Show sources on tier 1. Even a single attributed source makes a wrong high-confidence answer visible.
  7. Retrain on production traffic. Once real queries are collected under a retention policy, the largest open risk (R-01) becomes addressable.
24 · Glossary

Terms as used in this document

Banking77Public intent-classification dataset of 13,083 real customer-service utterances over 77 fine-grained banking intents.
CalibrationPost-processing that converts a classifier's uncalibrated scores into probabilities that can be compared against a fixed threshold. Here: sigmoid fitting over three cross-validation folds.
ConfidenceThe maximum calibrated class probability for a prediction. The routing signal — not a statement about answer correctness.
EscalationRouting a query to the most expensive tier because no cheaper source is trusted to answer it.
FAISSSimilarity-search library. Used here with an inner-product index which, over L2-normalised vectors, is equivalent to cosine similarity.
Inner product indexA flat index that scores a query against every stored vector by dot product — exact, not approximate, which is appropriate at fifty-nine entries.
Macro F1The unweighted mean of per-class F1 scores. Treats a rare intent as equal in importance to a frequent one.
MLflow projectA declared entry point, environment and parameter set that makes a training run reproducible by a single command.
RAGRetrieval-augmented generation. In this system the retrieval half is used on its own: an answer is returned from the knowledge base with no generation step.
Remote writeThe Prometheus protocol for pushing samples to a remote store — used where an inbound scrape cannot reach the container.
SBERTSentence-BERT. A transformer fine-tuned so that whole-sentence embeddings are directly comparable by cosine similarity.
TierOne of four answer sources, ordered by unit cost: conversational handler, template handler, RAG pipeline, LLM escalation.
