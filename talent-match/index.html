03 · SQL Matching Engine

17 CTEs. One query. Every employee scored at runtime.

The matching algorithm is a single parameterized SQL query. Any manager selects 1–3 top performers as benchmark — the algorithm computes medians, compares all 2,010 employees, and returns a ranked list. No precomputation, no hardcoded IDs.

Scoring formulas

-- Numeric TV (higher = better)
LEAST(100, ROUND(
  user_score / NULLIF(baseline_score, 0) * 100, 2
))

-- Inverse PAPI scales (lower = better)
LEAST(100, GREATEST(0, ROUND(
  (2 * baseline_score - user_score) /
  NULLIF(baseline_score, 0) * 100, 2
)))

-- Categorical (DISC, MBTI — exact match)
CASE WHEN user_val = baseline_val
  THEN 100.0 ELSE 0.0 END

-- CliftonStrengths overlap
ROUND(overlap_count::NUMERIC / 5 * 100, 2)
"The benchmark is never fixed. Any manager can define it at runtime by selecting 1–3 top performers as reference."

CTE architecture — 17 steps

CTE 1–2
benchmark_employees → unpack selected IDs; benchmark_psych → psychometric scores for those employees
CTE 3–6
baseline_psych, baseline_papi, baseline_competency → PERCENTILE_CONT(0.5) medians per TV across benchmarks
CTE 7–8
benchmark_disc_mode, benchmark_mbti_mode → MODE() WITHIN GROUP for categorical baselines
CTE 9
benchmark_strength_pool → pooled unique top-5 CliftonStrengths themes from all benchmarks
CTE 10–12
candidate_info, candidate_psych, candidate_papi → all 2,010 employees with org context and scores
CTE 13
candidate_strengths_overlap → top-5 theme overlap count per candidate vs benchmark pool
CTE 14
tv_match_rates_long → per-employee × per-TV match rate in long format (UNION ALL across all TVs)
CTE 15–17
tgv_match_rates → AVG within TGV; tgv_weights → hardcoded weights; final_match_rates → weighted total

07.5 · Limitations

Where the matching algorithm can still be wrong.

An honest read on failure modes — these matter before any manager acts on a ranked list.

Success pattern comes from a small benchmark set

The "success profile" in §02 is built from whichever employees were selected as R5 top-performer benchmarks. If that benchmark group happens to share an atypical trait unrelated to performance — same tenure cohort, same original department — the algorithm learns that trait as signal. There's no held-out group of independently-verified high performers to check the pattern against.

Missing assessment data silently changes the ranking

Not all 2,010 employees have complete Pauli, PAPI, and CliftonStrengths records. The 17-CTE query scores whatever is present; it doesn't flag or down-weight candidates with partial data, so someone with 2 of 5 assessments can rank above someone with all 5, for reasons that have nothing to do with fit.

No false-positive check

A candidate can score high on every measured trait (Pauli, PAPI Planning, CliftonStrengths themes) and still fail in the role for reasons the assessment battery doesn't capture — team fit, domain knowledge, timing. The system has never been checked against an actual promotion outcome, because no promotions have been made from its output yet.

No baseline against manager judgment

§01's "Without System" flow names bias and missed talent as the cost of manual judgment, but there's no historical data on how often manager-picked successors actually succeeded versus how the algorithm would have ranked them. The claim that systematic scoring beats gut-feel is directionally reasonable, not yet measured.

08 · Lessons Learned

What I would tell myself before starting this project.

ERD vs reality

The case study brief described GTQ1–GTQ5 and Tiki1–Tiki4 as separate columns. When I actually queried the live schema, the database turned out to store single composite values (gtq, tiki) instead. I only caught the mismatch by checking the real schema myself — documentation can lie.

Model availability

Partway through building this, my OpenRouter free-tier model got deprecated without any notice. I had to query the API live just to find out which model still worked. Lesson stuck: never hardcode a free-tier model name.

Supabase pagination

I didn't find out PostgREST caps requests at 1,000 rows until my query for all 2,010 employees came back short. I ended up writing a custom paginated fetch_table() to handle it properly — the kind of edge case you only hit once you're actually at scale.

EDA should challenge assumptions

I expected R5 employees to score higher on PAPI Leadership. They scored lower — and that turned out to be the most useful finding in the whole analysis. It's the moment I trusted the EDA over my own assumption, which is exactly when EDA is worth doing.

Future improvements

  • Longitudinal competency trend slope (over 5 years) instead of single latest-year score
  • Role-specific weight sets per job family — differentiated from generic success formula
  • Ensemble baseline using performance trajectory weighting, not just latest rating
  • Auto-generated personalized development plans for each candidate based on gap analysis
