00 · Origin

Nutrition apps are tedious. I wanted to fix that.

Every calorie tracker forces you to search a database, guess portions, and log everything manually. The friction is the reason people quit. What if the app did the thinking for you — from a single photo?

NutriPal started as an exploration: could I build a nutrition assistant that feels like having a personal nutritionist, not a spreadsheet? The goal wasn't just AI integration — it was building the entire product loop: onboarding, daily tracking, meal planning, food discovery, and fitness sync, all wired together with live data.

Three hard constraints shaped the architecture from the start:

  • AI must be the core, not a feature — Every major interaction should have AI behind it: photo analysis, meal planning, delivery curation, diet personalization.
  • Rate limits are a real engineering problem — Free-tier Gemini keys have strict quotas. A single-key setup would collapse under normal usage. I needed a solution baked into the infrastructure, not a workaround.
  • Data must feel live — Logging a meal and seeing the dashboard update without a page refresh isn't a nice-to-have. It's the difference between the app feeling like a product vs. a prototype.
"The photo is the interface. Everything else is infrastructure."

Realtime

State management without a state library.

I deliberately avoided Redux or Zustand. Instead, four custom hooks — useProfile, useDailyLog, useMeals, useDailyLogs — each subscribe to their own Supabase realtime channel. When any row changes in the database (from any device), the hook fires and the component re-renders. The result is live sync that feels like magic but is actually just well-scoped subscriptions.

This pattern also solved a common problem: stale AI output. When the Snap flow analyzes a photo and writes the result to Supabase, the dashboard hook picks it up immediately — no polling, no manual refresh, no prop drilling.

Why Zod schemas matter for AI output.

LLMs are non-deterministic. Without output validation, a single malformed response can crash the UI or silently show wrong data. Every Genkit flow in NutriPal defines both an input schema and an output schema using Zod. If Gemini returns something that doesn't match — wrong types, missing fields, out-of-range values — the flow throws before the data ever reaches the frontend. 

// Output schema for the food photo analysis flow
const AnalyzeMealOutputSchema = z.object({
  name:        z.string(),
  calories:    z.number(),
  macros:      z.object({
    protein:   z.number(),
    carbs:     z.number(),
    fat:       z.number(),
  }),
  healthScore:    z.number().min(0).max(100),
  expertInsight:  z.string().max(200),
  allergenWarning:z.string().optional(),
});
03 · Engineering Decisions

Three decisions that kept the app alive.

1
4-Key Rotation — solving rate limits at the infrastructure level

Why a pool, not a single key.

Free-tier Gemini keys have a low requests-per-minute cap. A single key fails the moment two users hit the app simultaneously. The naive fix — "just upgrade" — isn't useful for a portfolio app. Instead, I built a rotation wrapper: executeWithRotation tries key 1, catches any 429/quota/rate-limit error, then immediately retries with key 2, then 3, then 4.

This turned 4 free-tier keys into one production-grade key pool. The app never exposes a rotation error to the user — it's all invisible retry logic at the AI layer. 

for (let i = 0; i < GEMINI_KEYS.length; i++) {
  try {
    const tempAi = genkit({ plugins: [googleAI({ apiKey: GEMINI_KEYS[i] })] });
    return await fn(tempAi);
  } catch (error) {
    if (isRateLimitError(error) && i < GEMINI_KEYS.length - 1) {
      continue; // rotate to next key
    }
    throw error;
  }
}
2
Supabase Realtime — live dashboard without WebSocket complexity

Why custom hooks over a global store.

The alternative was a global state store (Redux/Zustand) that I'd manually update after every AI call. The problem: AI calls are async, errors happen, and keeping global state in sync with the database is a full-time job. Instead, I let the database be the source of truth and subscribed to it directly.

Each custom hook subscribes to a specific Supabase realtime channel scoped to the current user. When analyzeMeal writes to the food_records table, the useDailyLog hook fires and the dashboard re-renders — automatically, in real time, with no manual state update required.

3
Genkit over raw API calls — typed flows as the AI contract

Why a framework instead of fetch().

I could have called the Gemini API directly with fetch and parsed the JSON manually. But raw API calls mean untyped responses, no schema enforcement, and debugging that consists of logging strings and hoping. Genkit gives me typed input/output schemas, a local dev UI to inspect flow runs, and a clean separation between "AI logic" and "app logic."

Running npm run genkit:dev opens a local Genkit inspector where every AI flow can be tested in isolation with custom inputs — before ever touching the frontend. That drastically cut debugging time.

04 · User Journey

From onboarding to daily habit.

The product is designed as a loop: onboard once, use every day. Each screen connects to the next.

  • Onboarding
    Biometric setup in 2 steps. User enters gender, age, weight, height. App calculates BMI and category, sets calorie target, captures dietary restrictions and food allergies. All subsequent AI calls are personalized from this data.
  • Dashboard
    Command center for today. Energy balance with macro breakdown (protein/carbs/fat progress bars), hydration log, active burn from fitness sync, weekly macro trend chart, and a live daily food record with AI insights.
  • Snap
    Photo → nutrition in seconds. Camera or gallery upload triggers analyzeMeal. Gemini Vision identifies the dish, estimates portions, returns calories, macros, a health score, ingredients list, expert insight, and allergen warning if applicable.
  • Planner
    Manual or AI-assisted scheduling. Add a meal by name and let analyzeTextMeal auto-calculate nutrition. Or let generateDailyPlan generate a full day of breakfast/lunch/dinner with recipes and timing suggestions.
  • Explore
    Three discovery modes. Delivery Hub scores food delivery options against your profile. Recipe From Pantry generates creative recipes from ingredients you have. Predictive Path builds a complete meal plan with swap alternatives.
  • Profile
    Live updates downstream. Any change to biometrics or dietary restrictions immediately recalculates calorie targets and updates all AI recommendation context. Fitness Sync integrates mock wearable data to adjust Active Burn.
05 · What I Learned

Building AI products is infrastructure work.

The AI itself — calling Gemini, writing a prompt — is the easy part. The hard part is everything around it.

Prompt engineering is product design.

The allergen warning field in analyzeMeal was supposed to be simple — if conflict, warn. But early versions warned about everything: the model guessed at potential allergens that weren't present. The fix was a two-part instruction in the prompt: first, identify actual ingredients from the photo; second, check those specific ingredients against the user's allergy list. Framing matters more than phrasing.

Realtime is a product, not a feature.

The moment I wired Supabase realtime channels to the dashboard hooks, the app felt completely different — like a native app rather than a web form. The technical cost was minimal (a few lines per hook). The product impact was significant. This is now my default pattern for any data-driven feature: database as source of truth, realtime subscription as the state layer.

"Rate limits aren't a billing problem. They're an architecture problem."

The 4-key rotation was the clearest example of this: what looks like a cost/quota issue is actually a resilience design question. How do you build an AI app that stays up when one key degrades? The answer isn't "upgrade" — it's building a fallback mechanism that handles it transparently.
